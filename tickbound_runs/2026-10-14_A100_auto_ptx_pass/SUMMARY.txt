tickbound automatic PTX reorder pass (unroll-and-batch) on the five CUDA reorder harnesses - A100 80GB PCIe, 14 Oct 2026
vast 55860951 (~$0.20 of GPU time, destroyed). nvcc 12.6 image. ORIG = harness built with the real ptxas; AUTO = the same
harness built with tickbound's ptxas wrapper (tb_ptxas.py), which runs ptx_unroll on every PTX, transforming only the
harness's ORIGINAL kernels (TB_PTX_KERNELS). The hand variants (ro, ro2, ...) are untouched, so each harness's own
bitwise check "hand variant == orig output" inside the AUTO run compares the automatic kernel with the true original.

THE PASS (tickbound/src/tickbound/triton/ptx_unroll.py; wrapper tb_ptxas.py)
Every hand reorder that won on the 13 Oct H100 run is one transform: group k iterations of a strided loop, issue the
group's loads first, then the k bodies in order. The pass does it on PTX for any kernel (nvcc / NVRTC / Triton), with a
proof per load: loop with a single back-edge; prefix / suffix straight-line; induction registers updated once, purely,
in the suffix; a load's address a pure slice of induction registers + invariants (gathers: through another batchable
load); a load crosses a store only when both trace to different kernel parameters (param+offset provenance, integer
struct fields excluded); a loop with a block barrier only batches loads of buffers the kernel never writes; breaks
allowed (speculative in-range reads of read-only buffers); every copy's own loop test is emitted (a `!=` countdown is
not monotone). Unroll factor from a load budget: k = min(8, 16 // loads per copy). Output values are those of k
consecutive iterations of the original (same instructions, same order), so outputs are bit-identical.

WHAT THIS PROVES / DOES NOT
+ Fully automatic (a ptxas drop-in, no source edits, no AI), byte-identical, on an A100: 3.3x (stencil/scan),
  1.9-2.4x (search), 1.1-1.3x (gather), across three different kernel types and two libraries, reproducing the hand
  reorders' mechanism. The pass log says per loop what it did and why not.
- The unroll width must be chosen per loop by measurement, not a fixed budget: l2SelectMin1 needs 36 loads, llama
  needs 8 and no loop-1 batching. The measure-then-pick selector exists for Triton (tune.py); for CUDA it needs the
  harness (or a driver-API runner) to time k in {1,2,4,8} variants.
- Not covered: predicated loads inside the loop (Aerial), cross-loop hoists over a barrier (llama RO2), the bit-mask
  rewrite (find_index ro2) which is not a reorder.
